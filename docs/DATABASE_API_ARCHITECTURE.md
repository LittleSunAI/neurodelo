# Архитектура базы и API — шаг 17

## Граница этапа

На этом этапе не поднимаются PostgreSQL, Redis, Keycloak и отдельный backend. Подготавливается проверяемый контракт, по которому позже можно реализовать сервер без переделки интерфейсных сценариев.

## Слои данных

1. **Identity** — аккаунты, внешние identity, сессии, восстановление и устройства.
2. **Profiles** — публичная страница, роли, навыки, настройки и блокировки.
3. **Projects** — open-source проекты, участники, roadmap, роли и задачи.
4. **Git** — репозитории, issues, Pull Request, CI, коммиты и синхронизация.
5. **Contributions** — принятые вклады и проверка результата.
6. **Recognition** — благодарности, XP ledger, credits и аудит.
7. **Hero/Game** — герой, изображения, инвентарь, навыки, сезоны и бои.
8. **Community** — форум, чаты, реакции, вложения и жалобы.
9. **Moderation** — дела, доказательства, решения, апелляции и санкции.
10. **Notifications** — персональные события пользователя.

## Важные инварианты

- За один вклад создаётся не более одной основной карточки признания.
- Отмена XP не изменяет исходную операцию, а создаёт reversal.
- Пользователь не благодарит сам себя.
- Кодовый вклад получает XP только после принятия или merge согласно политике проекта.
- Закрытая переписка доступна только участникам разговора.
- Изображения героя принадлежат аккаунту и не доступны другим пользователям без явной публикации через профиль.
- Модерационные журналы и XP ledger не удаляются обычным пользовательским удалением.
- Внутренней денежной валюты и хранения платежей нет.

## Защита

RLS не заменяет серверную авторизацию, а дублирует критические ограничения. API обязан сначала проверить права в сервисном слое, после чего запрос к PostgreSQL дополнительно ограничивается политиками.

Администраторские операции должны выполняться отдельной server role. Пользовательскому соединению нельзя выдавать `BYPASSRLS`, права владельца таблиц или доступ к ciphertext Git-токенов.

## Версионирование API

Публичный контракт начинается с `/api/v1`. Несовместимые изменения создают `/api/v2`; расширение объекта необязательными полями остаётся в текущей версии.

Каждая операция имеет уникальный `operationId`. В следующем серверном этапе из OpenAPI можно сгенерировать:

- типизированный клиент;
- контроллерные интерфейсы;
- mock server;
- contract tests;
- документацию.
