# Архитектура признания и XP-журнала

## Разделение сущностей

### Вклад

`RecognitionRecord` описывает принятый результат: автора, проект, тип работы, связь с задачей, подтверждение, релизы и благодарности.

### XP-операция

`XpTransaction` является отдельной записью. Она хранит:

- участника;
- проект;
- вклад;
- тип начисления;
- Skill XP;
- Hero XP;
- искры сообщества;
- источник;
- причину;
- статус;
- признаки риска.

Карточка вклада не является самим балансом XP. Это позволяет менять правила начисления без потери авторства.

## Отмена ошибочного XP

Операция не удаляется. Создаются:

1. статус `reversed` у исходной записи;
2. новая операция `reversal` с отрицательными значениями;
3. запись в `RecognitionAuditEvent`;
4. отметка карточки вклада о пересмотре.

Так история остаётся объяснимой и не может быть незаметно переписана.

## Защита от накрутки

- одна публичная благодарность пользователя на один вклад;
- Skill XP не начисляется кнопкой благодарности;
- крупные начисления должны приходить от Git, проекта или проверяющего;
- повторная отмена одной операции запрещена;
- жалоба создаёт запись для будущей модерации;
- все корректировки сохраняют причину и автора.

## Release credits

`ReleaseCredit` связывает версию проекта с участниками и конкретными вкладами. Эта сущность позволяет показывать авторов релиза независимо от количества строк кода.

## Денежная поддержка

`SupportLink` хранит только внешнюю HTTPS-ссылку. Платформа:

- не принимает оплату;
- не хранит деньги;
- не выступает посредником;
- не конвертирует искры в деньги.

## Переход на backend

При `NEXT_PUBLIC_USE_FALLBACKS=false` gateway обращается к `/api/v1/recognition/*`. Будущий сервер должен обеспечить:

- транзакционное начисление XP;
- неизменяемый аудит;
- проверку полномочий мейнтейнера;
- идемпотентность операций;
- защиту от повторного начисления;
- модерацию жалоб;
- безопасную валидацию внешних ссылок.
